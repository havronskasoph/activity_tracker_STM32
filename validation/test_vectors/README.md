# Тестові вектори ПК ↔ MCU

50 вікон із тестової вибірки, по 10 на кожен клас, з очікуваними виходами
розгорнутої моделі `st_ign_realworld_imu_27hz`, порахованими на ПК.
Форма вікна — 55 × 6 при 27.45 Гц.

Генеруються `validation/run_all.py`, вручну не редагуються.

## Що саме перевіряється

Вікна тут **уже нормалізовані** — `(x - mean) / std` застосовано. Вони подаються
прямо в модель, минаючи `har_preproc`. Це зроблено навмисно: тест відповідає на
одне питання — **чи рахує C-модель на платі те саме, що модель на ПК**. Якщо
подавати сирі відліки, у розбіжність домішався б ще й препроцесинг, і причину
було б не відокремити.

Препроцесинг перевіряється окремо: фільтр — тестом 5
(`validation/tests/test_05_preprocessing_parity.py`), а повний тракт на платі —
записом реального сигналу.

## Файли

| Файл | Формат | Для чого |
|---|---|---|
| `test_vectors.npz` | `x_normalized` (50, 55, 6) float32, `x_raw`, `y_true`, `y_pred`, `proba`, `subject` | сторона ПК, звірка результатів |
| `har_test_vectors.h` | C-масив `har_tv_input[50][55][6]` + `har_tv_expected[50]` | вкомпілювати в прошивку |
| `expected.csv` | таблиця з істинним і очікуваним класом та ймовірностями | ручний перегляд |

## Як прогнати на платі

1. Поклади `har_test_vectors.h` у `Core/Inc/` прошивки.
2. У `main.c` після `har_model_init()` додай разовий прогін:

```c
#include "har_test_vectors.h"

int ok = 0;
for (int i = 0; i < HAR_TV_COUNT; i++) {
    float probs[HAR_CLASS_COUNT];
    int cls = -1;
    if (har_model_predict(&har_tv_input[i][0][0], probs, &cls) == HAR_MODEL_OK) {
        if (cls == har_tv_expected[i]) ok++;
        printf("# tv %d expected=%d got=%d\r\n", i, har_tv_expected[i], cls);
    }
}
printf("# tv match=%d/%d\r\n", ok, HAR_TV_COUNT);
```

3. Зніми вивід із UART і порівняй: рядок `# tv match=` має показати **≥ 49 з 50**
   (критерій 98 %).

Пам'ять: масив займає близько 66 КіБ Flash. Після звірки прибери `#include` і
цикл, щоб не возити вектори у робочій прошивці.

## Якщо збіг нижчий за 98 %

Найімовірніші причини, у порядку спадання ймовірності:

1. **Порядок осей.** Модель чекає `[час][канал]` (channels-last). Якщо Cube.AI
   згенерував вхід у іншому порядку — виходи будуть осмислені, але неправильні.
2. **Подвійна нормалізація.** Вектори вже нормалізовані; якщо прошивка застосує
   `har_preproc_normalize` ще раз, вхід поїде.
3. **Квантування.** Якщо на платі int8-модель, кілька вікон біля межі рішення
   можуть розійтися — це і є причина, чому критерій 98 %, а не 100 %.
